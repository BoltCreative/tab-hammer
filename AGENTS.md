# Tab Hammer — agent and contributor guide

Tab Hammer is a Manifest V3 Chrome extension (TypeScript + React + Vite) that shows every Chrome window, tab group, and tab as an outline, in its own window or docked in Chrome's side panel, plus an MCP server that lets an AI agent such as Claude Code read and rearrange tabs through the extension. It's an npm workspaces monorepo: `packages/extension` (the extension), `packages/mcp` (the publishable `tab-hammer-mcp` npm package: MCP server, native messaging host, and installer), `packages/protocol` (message types both compile against).

This file is for AI coding agents and human contributors alike. `CLAUDE.md` just imports it. Maintainers can keep machine-specific notes in a gitignored `CLAUDE.local.md`.

## Worktree setup

If you work in a git worktree, run `npm install` at the worktree root after `git worktree add`. A fresh worktree has no `node_modules/`, and Node's resolver silently walks up to the main checkout's instead of failing.

## Docs

`docs/superpowers/` holds the design records written while building Tab Hammer: design specs (`specs/YYYY-MM-DD-<topic>-design.md`) and implementation plans (`plans/YYYY-MM-DD-<topic>.md`). They are historical: they explain why things were built the way they were, but the code and this file describe the current state, and the docs aren't updated when later work changes the design. Add a new spec and plan for substantial new work rather than editing old ones.

## Branches

Work lands on `dev` through pull requests; `main` is the release branch and takes only `dev` (CI's `source` job fails a pull request into `main` from any other branch). Both rulesets require a pull request and the `gate` check, and `main`'s also requires `source`. Merging to `main` only runs CI; nothing deploys until a maintainer runs the Release workflow on `main` (`.github/workflows/release.yml`).

## Completion gates

Pick the gate by change class. Report the gate name and result when declaring work complete.

| Gate            | Command        | When                                                                                                                      |
| --------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Docs-only diff  | (none)         | Every changed path is `.md`.                                                                                              |
| Any code change | `npm run gate` | typecheck + lint + format check + unit (Vitest) + `build:e2e` + e2e (Playwright, real Chromium with the built extension). |

Run it once on the final commit. CI (`.github/workflows/ci.yml`) runs the same checks on every pull request, split into parallel jobs: `checks` (typecheck, lint, format check, unit) and three `e2e` shards (`build:e2e` and a third of the Playwright suite each). Together they must stay equal to `npm run gate`, so a change to one changes the other. Its `gate` job is the check to require: it passes when the others did, or when a PR changes only Markdown (they're skipped then). The e2e suite launches its own throwaway Chromium profile per test, so tests run in parallel (a quarter of the cores locally, since each runs a whole Chromium; every core on CI); it never touches your own Chrome.

The gate builds into `packages/extension/dist-e2e/` (`npm run build:e2e`), and the e2e fixture loads the extension from there. `~/.tab-hammer/dist` belongs to the developer's dev Chrome: every tree's `npm run dev` server writes it and that Chrome loads it, so never build into it from a gate or test run. Agents must never run `npm run dev` themselves; the developer runs the dev server. `dist/` is only the `npm run build` output. To run e2e alone, `npm run build:e2e` first; pass Playwright arguments after `--` (`npm run test:e2e -- tests/e2e/bridge.spec.ts`).

Agents must never run `npm run install-mcp`, `tab-hammer-mcp install`/`uninstall`, or `npm publish`: the installer writes into the developer's browser profile folders, the Windows registry, and their agent harness configs. Installer tests run against a fake machine in a temp folder (`packages/mcp/src/__tests__/fakeEnv.ts`), and the built-package test runs the CLI with a temp `HOME` and an empty `PATH`.

The e2e suite runs headless (new-headless Chromium). Headless Chromium ignores window focus changes, so window focus is asserted via recorded `chrome.windows.update` calls rather than by observing which window is focused. It must stay headless: developers keep working on the same machine while gates run, and headed windows steal their workspace.

## Store build and releases

`npm run build:store` (`TAB_HAMMER_STORE=1`) builds the Chrome Web Store package into `packages/extension/dist-store/` and zips it to `packages/extension/release/tab-hammer-<version>.zip` (`scripts/pack-store.ts`). It has no manifest `key` (the store rejects one) and signs in to Drive with `STORE_GOOGLE_OAUTH_CLIENT_ID` from `src/shared/syncConfig.ts`, not the dev client; while that's empty the store build has Drive sync off. It never touches `~/.tab-hammer/dist`, so it's safe to run. `npm run release -- patch|minor|major|x.y.z` (`scripts/release.ts`) bumps the release version (`RELEASE` in `src/manifest.ts`), every package.json, and package-lock.json together, without committing. `.github/workflows/release.yml` (Release, run by hand on main) is the only deploy, in three independent jobs: `store` builds the store package with `TAB_HAMMER_BUILD` (main's commit count) as the version's fourth part, uploads it as the store draft through the Chrome Web Store API v2 (`packages/extension/scripts/cws.ts` and `cwsClient.ts`), tags the commit `store/<version>`, and submits the draft for review (skipped while the store secrets aren't set); `npm` publishes `tab-hammer-mcp` through npm trusted publishing (GitHub OIDC, no token) unless npm has that version; `registry` then lists `server.json` in the MCP registry with `mcp-publisher login github-oidc` unless the registry has that version. Each skips what's already out, so running it again is safe. The steps and the one-time setup are in `docs/store/release.md`. Every permission's reason is commented in `src/manifest.ts`; keep `docs/store/listing.md`'s justifications in step with it.

## Icons and store images

The extension icons are rendered, not drawn by hand: `packages/extension/icons/icon.svg` (the full drawing: indigo gradient tile, shadow, shaded claw hammer) renders the 32, 48, and 128px PNGs, and `icon-16.svg` (a flat redraw on the 16px pixel grid, since the full drawing's thin handle blurs at 16px) renders the 16px one, through `npm run render-icons -w @tab-hammer/extension`. Edit an SVG, re-render, and commit the PNGs with it. 32px keeps the full drawing because Chrome draws the toolbar icon at 16pt, 32px on a Retina screen. The icon's tile colours aren't app theme tokens: the view's colours live in `src/view/styles/theme.css`, and window header colours are Chrome's tab-group colours picked per window (`src/model/windowColor.ts`).

The Chrome Web Store screenshots and promo tiles in `docs/store/images/` (also the README's screenshot) are rendered by `npm run store-assets -w @tab-hammer/extension` (`scripts/store-assets.ts`): it builds `dist-e2e`, stages a made-up outline in headless Chromium against fake pages served through routes, and composes each image as HTML. It's tooling, not part of the gate. Window colours come from random window IDs, so they change from run to run. Rerun it after a visible UI change and commit the images; `docs/store/listing.md` says which image is which.

## Architecture

Extension paths below are relative to `packages/extension/`. Chrome window and tab IDs are not stable across restarts, which is why the outline carries Tab Hammer's own IDs.

### Service worker and the outline

- The service worker opens or focuses the Tab Hammer popup window, on a toolbar click or its shortcut (the manifest's `_execute_action` command, Alt+Shift+H by default, which Chrome treats as the click, side panel included).
- It owns the outline (`src/background/outline/`): a record per window, group, and tab, keyed by Tab Hammer's own random IDs and kept in IndexedDB `tab-hammer-outline`. Chrome's IDs are attached only while a record is live. Chrome events are reconciled into it through a serial queue.
- Window order is Tab Hammer's own (Chrome has none): the order of the outline's window list. The store's meta persists it, a re-linked window keeps it (the matcher replaces the saved record in place), and a sync file carries it as its window order, so the sync schema has no order field. `src/model/outline/order.ts` moves windows (drag, Alt+Up/Down, a new window's row after the current window).
- A fresh browser launch is told apart from a worker restart by `browserSession` (the single instance in `src/background/session.ts`). After a launch, every window that was open at shutdown is kept hibernated, marked open-at-shutdown (never trashed: a quit, crash, or kill isn't the user closing it, and Chrome may restore nothing), and restored windows are re-linked to their saved records once their tabs stop changing (a quiet period), by the pure matcher in `src/model/outline/`.
- Closing a tab in Chrome removes its row, and closing a window by hand while Chrome runs moves it to the trash, hibernated tabs and all; that's the only way Chrome trashes a window. Hibernating a window or tab closes it in Chrome but keeps its rows, dimmed, to reopen on click. Reopening a closed window whole opens the tabs that were live when it closed and keeps the rest hibernated (`liveAtClose`; with none marked, every tab opens). Deleting moves a row to the trash, and the Recently closed section restores trashed rows for seven days: ↺ reopens one in Chrome (one deleted while hibernated comes back hibernated, `hibernatedAtClose`), the section's Restore all does that for every one, and its tabs preview in the panel.
- Windows Tab Hammer opens itself (including through the Claude bridge) are recorded as known, never re-linked. Windows and tabs it is closing are left out of reconciling until Chrome reports them gone.

### Previews and capture

- The service worker screenshots each window's visible tab as the user browses (`src/background/previews.ts`) into an IndexedDB store keyed by page URL (`src/shared/previewStore.ts`), which the view reads for the tab preview panel.
- When the panel shows a window's visible tab with no preview, the view asks the service worker to capture it on demand, without the debugger.
- Background tabs are screenshotted through `chrome.debugger` and CDP `Page.captureScreenshot`, attached only for the shot (`src/background/debuggerCapture.ts`, one at a time through `captureQueue.ts`), and only from the explicit Refresh runs (`allowDebugger` on the capture request). The debugger's "started debugging this browser" infobar pushes the outline down under the pointer, so a hover must never attach it.
- The service worker records each window's and each on-demand tab's latest capture outcome (saved, or which rule skipped it, or the error) in `chrome.storage.session` (`src/shared/captureOutcomes.ts`); the preview panel shows it when a tab has no preview.
- Window captures share one scheduler (`captureScheduler.ts`) with a per-capture time limit, so one hung Chrome call can't stall the rest.
- The Capture missing (tabs with no preview) and Refresh all actions run those captures for every tab, one at a time, from the view (`src/view/refresh/`). They wake sleeping tabs (discarded, or not loaded since a restart) with a background reload first, and the panel's "Capture missing" hint follows the same rule (`backgroundTabNote`).
- Previews never go stale: one is how the page looked the last time the user had it on screen, kept until they look at it again or ask for Refresh all.
- A preview is kept exactly as long as this computer's outline uses its address (`previewKey`, fragment ignored): any window record, live, hibernated, or trashed, with a tab there. Other computers' outlines don't count, and there's no age or size limit. The outline's change hook (coalesced) and each worker start run `previewPrune.ts`, which reads the outline after its queued work plus the pages Chrome has open, and deletes the rest except shots saved since it started reading (a capture can land before the outline reconciles its tab's new address).
- Previews never follow Chrome's history: clearing browsing data leaves them.

### View

- The view doesn't read Chrome for the tree: it subscribes to the outline over the `tabHammer.outline` port (`src/view/chrome/outlineClient.ts`) and sends commands (rename, hibernate, delete, restore) as runtime messages.
- `src/model/buildTree.ts` turns the outline into the window/group/tab view model, and `src/view/chrome/chromeSource.ts`, the only view module that touches `chrome.*` (permission checks and requests live in `src/view/chrome/permissions.ts`), keeps just the direct live actions (activate, focus, move, close). `src/model/selection.ts` is the pure multi-select reducer. Then it renders React components.
- The view has a fixed header above the outline and a fixed preview panel below it, and only the outline list scrolls between them. The search box, the Actions menu, live progress (with Stop), and banners go in that header (`src/view/header/AppHeader.tsx`), never in the scrolling list.
- Bulk actions (New window, Close duplicates, Capture missing, Refresh all, Keyboard shortcuts, Clear previews) live in `src/view/header/useHeaderActions.ts` and appear in both the header's Actions menu and a right-click on the outline's background. Add new ones there, not as header buttons.
- Keys are search-first, like a command palette (`navIntent` and `typesIntoSearch` in `src/model/keyboardNav.ts`, one `keydown` listener on the document in `App.tsx`, so each docked panel's page has its own). Focus lives in the search box (a combobox): typing anywhere with no other text field focused focuses it during the keydown, so the key lands there, and every text-editing key (←/→, Space, Backspace, Home/End) is the search box's. Only ↑/↓ (⇧ extends the selection, ⌥ moves the window, ⌘ opens or goes up a level), ⌘⌫ (trash), Enter and Esc (search, then selection) drive the outline; ⌘ is Ctrl off a Mac. The cursor row is the search box's `aria-activedescendant` (rows carry an `id` and `data-cursor`), kept scrolled into view, and it runs on past the last window into Recently closed's rows (`trashRows`), which it never selects or trashes. Rename fields stop their keys' propagation, the devices panel is `data-own-keys`, and an open menu or a handler that prevents a key's default (the preview's resize edge) keeps it.
- Every view shortcut is a row of one table, `SHORTCUTS` in `src/model/shortcuts.ts`: the handlers (`navIntent`, `viewShortcut`, App's Escape) act only on a press `shortcutOf` finds there, and the Keyboard shortcuts sheet (`src/view/header/ShortcutsPanel.tsx`, from the Actions menu or ⌘', in the header's banner area, Esc closes it) and the tooltips render from it, ⌘ as Ctrl off a Mac. A unit test checks the handlers act on exactly the keys the sheet lists. Add a key to the table, then handle its id. The sheet also shows the open-Tab-Hammer shortcut as Chrome has it (`chrome.commands.getAll()`, `src/view/chrome/commands.ts`, "not set" when empty) with a Change… button that opens chrome://extensions/shortcuts through `chrome.tabs.create`.
- Current tabs (an icon toggle in the header, highlighted while on, ⌘/) shows each live window's header and only its active tab, hibernated windows as bare headers (`src/model/currentTabs.ts`, a view filter; the outline is untouched). A search overrides it while the query is non-empty. ↑/↓ step through the current tabs (live windows' headers drop out of the cursor's path), and Enter, ⌘↓ or a plain click activates the tab and focuses its window. It's remembered in `chrome.storage.local` (`src/view/chrome/currentTabsSetting.ts`) and every view follows storage changes, so the standalone window and each docked panel flip together.
- Recenter (the header's crosshair, ⌘\\) puts the current window's active tab in the middle of the list with the cursor on it, expanding a collapsed window or group and leaving any search. In a docked panel the current window is the panel's own window; in the standalone window it's the last-focused normal Chrome window (the card marked focused), and with none focused yet recenter does nothing. A docked panel recenters on its window when it opens.
- The preview panel (`src/view/preview/PreviewPanel.tsx`) takes its own space in the window's column, so it never covers rows. It shows the tab last hovered (after a short rest) or moved to with the keyboard cursor, and keeps it when nothing is hovered (`usePreviewTarget.ts`). It collapses to a thin bar and resizes from its top edge, and both are remembered in `chrome.storage.local` (`src/view/chrome/panelSettings.ts`). There is no floating hover card.
- Window headers are sticky section bars in a colour picked from the window's Tab Hammer ID (`src/model/windowColor.ts`).
- Drag and drop (`src/view/components/useRowDrag.ts`): windows dragged onto a window header's top or bottom edge, or into the gap under a window, reorder (a bar between windows); onto the header's middle they merge (the header floods, labelled). While tabs are dragged, a "Drop here for a new window" strip sits in its own space under the list, and the worker's `moveToNewWindow` moves them into a new window at the end. A right-click on tab or group rows offers "Open in new window", the same move with the row after the tabs' window.
- Windows Tab Hammer opens for New window or a new-window move open in the background (unfocused): they're rows to fill, not places to go. A docked panel opens itself in such a window (`dockInto`) while Chrome still counts the click.

### Docked mode (side panel)

- Docked mode (`src/background/dock.ts`, the view's half in `src/view/chrome/dock.ts`, shared messages in `src/shared/viewMode.ts`): the same view runs in Chrome's global side panel from `src/view/panel.html` (it only adds `data-surface="panel"`), instead of the standalone window ("float").
- Only a page holding the user's click may call `sidePanel.open`, and that click lasts about 5 seconds, so the view fires the opens all at once: the standalone window's Dock button opens the panel in every normal window and then tells the worker, which remembers the mode (`viewMode` in `chrome.storage.local`), sets `openPanelOnActionClick` so a toolbar click opens the panel in that window (Chrome does it, and `action.onClicked` doesn't fire), and closes the standalone window.
- Windows opened later get a panel from a toolbar click there, or from any click in any docked panel: each docked panel holds a `tabHammer.panel` port naming its window, and a click asks the worker which normal windows have none, less those the user closed it in (kept in `chrome.storage.session`).
- Pop out (a panel's button) sets float, opens the standalone window, then closes every panel (`sidePanel.close`, Chrome 141+, no click needed). Both buttons are one icon toggle in the header's toolbar.
- A docked panel knows its browser window (`chrome.windows.getCurrent`): it marks that window's card (glyph filled in, `aria-current="location"`) and opens recentered on its active tab; the order is the same in every view. Only the standalone window answers the worker's view ping, so a panel never makes a blank standalone window look alive.
- The panel's side is the user's Chrome setting, readable through `sidePanel.getLayout()` (Chrome 140+) but not settable: the root gets `data-side` so the panel's border faces the page, and a docked panel's Actions menu (Panel side…) and the toolbar icon's right-click menu (`chrome.contextMenus`, made on install) open Chrome's setting, which moves every side panel in every window. The layout works from Chrome's minimum panel width, about 360px, which the extension can't change.

### Sync

Sync lives in `src/background/sync/`, with pure logic in `src/model/sync/`.

- Each install writes one file, `outline-<installId>.json` (its exported outline, trash included), to Google Drive's hidden app-data folder, and only reads the others', so there's no merging.
- The sync engine (`syncEngine.ts`) pushes 10s after the outline last changed (a dirty flag in `chrome.storage.local` survives a worker restart), and pulls every 5 minutes (`chrome.alarms`) and when the picker opens. It downloads only files whose Drive modified time changed into a local cache (IndexedDB `tab-hammer-sync`), and validates every file against the schema both ways (`src/model/sync/schema.ts`).
- Nothing remote changes this computer's outline except Restore all, or the self-restore of an install whose outline database started empty (no push happens until that check is done). Self-restore brings the file's live windows in as re-link candidates and runs the restart matcher over the open windows, so they don't show twice.
- Checkpoints are dated snapshots of this computer's outline, local and in Drive, one a day plus one before anything drastic, pruned to 14 daily then 8 weekly.
- Drive sits behind `SyncBackend` (`driveBackend.ts`: REST with `fetch`, `chrome.identity.getAuthToken`; a 401 drops the cached token and retries once). Drive sync is off until `GOOGLE_OAUTH_CLIENT_ID` in `src/shared/syncConfig.ts` is set; the manifest's `oauth2` block exists only then, and never in the e2e build.
- Chrome Sync devices (phones included) come from `chrome.sessions` (`devices.ts`), no Drive needed. `sessions` is an optional permission: the devices panel offers a button that requests it from the click (`src/view/chrome/permissions.ts`), and until it's granted `chrome.sessions` is undefined and the worker reports no devices. Chrome defines it in the running worker once granted, so `devices.ts` reads `chrome.sessions` at each call.
- The Actions menu's "Other devices…" opens a devices panel in the header's banner area (`src/view/sync/`). It shows any of them, or a checkpoint, read-only in place of the outline (its banner also in the header), with Open here (a copy with new IDs), Restore all (missing windows come in hibernated, and ones in this computer's trash come back out of it), and Forget. It talks to the worker over the `tabHammer.sync` port and sync command messages.

### Claude bridge (MCP)

- An agent harness (Claude Code, Codex, Cursor, …) starts the MCP server (`packages/mcp/src/main.ts`, stdio). The browser starts the native messaging host (`packages/mcp/src/host.ts`) when the service worker connects (`src/background/bridge.ts`, at startup and on toolbar click; it retries with backoff if the host exits, and stops if the host isn't installed).
- The two meet on a Unix socket (`~/.tab-hammer/bridge.sock`), or on Windows a per-user named pipe (`\\.\pipe\tab-hammer-<user>`); `TAB_HAMMER_SOCKET` overrides it (`paths.ts`). The host only relays, rewriting request IDs so several agent sessions can share one browser connection; the service worker runs each command (`src/background/tabCommands.ts`).
- The bridge is live-only: it never sees hibernated or trashed rows.
- `packages/mcp` is the `tab-hammer-mcp` npm package. `npm run build -w tab-hammer-mcp` (`build.ts`, rolldown) bundles three self-contained plain-JS files into `dist/`: `cli.js` (the bin), `server.js` (the server with its npm dependencies inlined), and `host.js`, which must import nothing but Node built-ins and `@tab-hammer/protocol` (the build enforces it). So the package has no runtime dependencies and runs on Node 22+. `server.json` is its MCP registry listing; its `name` and `version` must match `package.json`'s `mcpName` and `version` (a test checks).
- `npx tab-hammer-mcp install | uninstall | doctor` (`src/install/`). Install copies `server.js` and `host.js` plus a launcher (a shell script, or `.bat` on Windows) to `~/.tab-hammer/mcp` (`%LOCALAPPDATA%\TabHammer\mcp`), pinned to the installing `node` (`deploy.ts`). The browser never runs the host from the repo or npx's cache: macOS blocks browser-launched programs from reading `~/Documents` until the user approves a prompt, so a host run from the repo hangs silently.
- It registers the host for each browser that has been run (its user data folder has a `Local State` file) (`browsers.ts`: a manifest in each NativeMessagingHosts folder on macOS and Linux, an HKCU key per browser family on Windows; Brave on macOS reads Chrome's folder), with the dev extension ID and `STORE_EXTENSION_ID` (`packages/protocol`, the store listing's ID) as allowed origins. It registers the server with each harness found (`harnesses.ts`, formats sourced from each vendor's docs; Claude Code through its CLI, the rest by editing JSON or TOML).
- Config edits insert one run of text and record it in `install-state.json`, and uninstall cuts exactly that back out (`jsonEdit.ts`, `tomlEdit.ts`), so install then uninstall is byte-identical. Everything machine-specific (OS, folders, registry, running `claude`) comes through `InstallEnv` (`env.ts`), so tests inject a fake one.
- `doctor` checks the deployed files, each browser's registration, a live `list_tabs` through the socket, and each harness entry, and says when npm has a newer version than the one deployed (`version.ts`; a warning, not a failure). Since install copies the server out, a new release only reaches a machine when install runs again. Only doctor asks npm; the server never touches the network. `TAB_HAMMER_NO_UPDATE_CHECK=1` skips the check.
- In the repo, `packages/mcp` source runs as TypeScript directly on Node 22.18+ (type stripping): erasable syntax only, `.ts` import extensions.

### Dev server quirks

- In `npm run dev`, crxjs's service worker forwards every request to the extension's own origin to the Vite server; `build/faviconPassthrough.ts` exempts Chrome's `_favicon/` endpoint, and any other Chrome-served extension URL would need the same.
- crxjs also reloads the whole extension whenever a file the service worker imports changes. `build/holdBrokenReloads.ts` holds that reload while the service worker's files don't link (a half-finished edit), since a service worker that fails to start takes crxjs's reload client down with it and the extension stays dead until reloaded by hand.
- `build/mcpAutodeploy.ts` keeps the developer's installed MCP (`npm run install-mcp`) in step with the tree `npm run dev` runs in. Only if `install-state.json` exists in install's deploy folder (`layout()`), on start and after changes under `packages/mcp/src` or `packages/protocol/src` (debounced, `__tests__` ignored), it builds the package into a temp folder (`node packages/mcp/build.ts <dir>`) and copies over whichever of `host.js` and `server.js` differ, through `deployHost`/`deployServer` with the node install recorded, so the launcher stays pinned. It never installs, and never touches browser registrations or harness configs. A new `host.js` stops the running host (processes whose command line has the deployed `host.js` path as an argument, found with `ps`; not on Windows, where it asks for an extension reload instead), and the bridge's reconnect starts the new one; a new `server.js` logs that the agent needs a restart. A failed build logs and leaves the deployed copy alone. The installer and deploy modules load at run time, not through the config bundle, because Vite restarts the dev server whenever a config dependency changes.

### Optional maintainer tooling

`.skullet/` holds config for Skullet, a dev-environment tool the maintainers use to run `npm run dev` as a service in whichever worktree they're working in. It's optional; nothing in the build or tests depends on it.

## Tests

Tests must be deterministic: the same code passes on a fast laptop, a busy one, and a two-core CI runner, every time. A smaller suite is better than one that can fail on a slow or different machine, so **delete a test rather than keep it flaky**, and cover its logic in unit tests instead.

- Banned in tests: sleeps and fixed waits (`waitForTimeout`, `setTimeout`), per-call timeouts (`{ timeout }` on an `expect`, a poll, or an action), retries, and any assertion on how long something took. The config's `timeout` and `expect.timeout` (`playwright.config.ts`) are hang guards, far above any real test's duration; never tune them. A test that gets near them is too big: shrink it (fewer tabs, a smaller viewport).
- A wait (`expect.poll`, a web-first `expect`) may only wait for a state that is certain to arrive once work already started finishes: an outline record, a Chrome tab loaded, a row rendered. Never one that a timer, Chrome's scheduling, or the machine's speed decides. Before pointing at rows, wait for the view to show everything the test built (`synced` in `fixtures.ts`), so a late update can't move a row under the pointer.
- The app's own timers never decide a test's outcome. Ones a test would have to outwait are stepped by a test hook (restart re-link's quiet period: the e2e build has none, and tests call `settle` once Chrome has restored what they expect; sync pushes only on `syncNow`); time limits and status timeouts are off in the e2e build (`limitMs` in `src/shared/e2eBuild.ts`, Vite mode `e2e`); the timers' own behaviour is unit-tested with fake clocks. `E2E_BUILD` may only switch timers, never product behaviour. A new timer in a path an e2e test runs through goes through the same switch.
- Don't assume the platform or headless Chromium's behaviour beyond what's documented here (window focus, below). Where it differs by OS, use a hook or assert on recorded calls.
- To prove a change to the suite, run it repeated (`npm run test:e2e -- --repeat-each=10`) on CI and locally under load, with zero failures.

- Unit: `packages/*/src/**/__tests__/` (and `packages/extension/build/__tests__/` for the Vite plugins: the reload hold run against the installed crxjs, the MCP autodeploy against a temp deploy folder with a fake build and host stop; and `packages/extension/scripts/__tests__/` for the store client). Pure logic only.
  - Extension: model; outline model (`src/model/outline/`: lifecycle, matching, reconcile, match application, open/place); outline store (against `fake-indexeddb`) and settle tracker (`src/background/outline/`); browser-session renewal; capture scheduling; per-window and on-demand debugger capture with an injected `chrome`; the capture queue; preview policy and the preview pruner; sync (`src/model/sync/`: schema validation, Restore all, Open-here copy, checkpoint retention, device list; `src/background/sync/`: the engine against an in-memory backend with a fake clock, the Drive backend against `tests/fakeDrive.ts`, the sync store, `chrome.sessions` with a stubbed `chrome`).
  - Store: the Chrome Web Store client (`packages/extension/scripts/__tests__/`) against a stand-in store: request shapes, the service account JWT, and a pending review holding back uploads and submissions.
  - MCP: native messaging framing; a functional test running the real MCP server process against the real relay with a stand-in extension; and the installer (`src/__tests__/`, which build `dist/` first): per-OS browser and harness path resolution (Windows paths via `path.win32`), the JSON and TOML config writers' byte-identical round trips, install/uninstall/doctor against a fake machine (Windows simulated with a fake registry), and the built CLI run in a child process with a temp `HOME`.
- E2E: `packages/extension/tests/e2e/`.
  - `bridge.spec.ts` covers the whole Claude → Chrome path: it deploys the built native host (`packages/mcp/dist/host.js`, which `npm run build:e2e` builds) into a temp Chromium profile's `NativeMessagingHosts` folder, lets Chromium launch it, and drives tab commands through the real MCP server.
  - The fixture opens the view through the service worker's `tabHammer.openOrFocus` test hook, the same code path as the toolbar click.
  - Chrome refuses to screenshot `data:` pages, so preview tests serve http pages through Playwright's `context.route`.
  - `sidePanel.spec.ts` covers docked mode: Dock opening real (headless) side panels in every window, a panel click opening it in newer windows but not where the developer closed it, Pop out, the mode surviving a restart, the 360px layout and its border following the side, Panel side… opening Chrome's setting, and a panel opening scrolled to its own window. Playwright can't reach a side panel's page, so a panel's clicks are driven on `panel.html` opened as a tab, which doesn't register itself as a panel.
  - `outline.spec.ts` covers the outline's lifecycle in the live view (hibernate, delete, reopening as closed, Recently closed and its Restore all). `restart.spec.ts` also kills Chromium with SIGKILL, and quits it, then relaunches without restoring, to check the windows come back hibernated.
  - `currentTabs.spec.ts` covers Current tabs (one row per window, following the active tab live, search overriding it, the setting surviving a reopen, ↓/Enter/click focusing the window, asserted on recorded `chrome.windows.update` calls) and recenter (a 12-tab window's middle tab in a short viewport, collapsed window and collapsed group, from a panel page opened as a background tab in that window; and in the standalone window, on the last-focused window, which the `focusWindow` hook sets since headless Chromium sends no focus events on macOS).
  - `shortcuts.spec.ts` covers the Keyboard shortcuts sheet: the Actions menu and ⌘' open it, it lists the open shortcut Chrome reports, Escape closes it, and Change… opens chrome://extensions/shortcuts.
  - `windowOrder.spec.ts` covers reordering windows (edge drop vs merge middle, Alt+Up/Down), New window, dropping tabs for a new window, and Open in new window. Playwright's drag sends dragover only on moves within an element, so its helper ends with a one-pixel move.
  - `restart.spec.ts` is a real restart: it closes Chromium and relaunches it on the same profile with `--restore-last-session`, waits until Chrome has restored and loaded the expected tabs, settles (`settle`), and checks restored windows re-link to their rows (served by a local page server, since restored tabs load before Playwright can route them).
  - `sync.spec.ts` runs two installs (two temp profiles) against one fake Drive (`tests/fakeDrive.ts`, served over HTTP by the test): the devices panel, Open here, Restore all, checkpoints, and a wiped profile's self-restore re-linking its open windows. Tests never reach Google.
  - Test hooks on the service worker's `tabHammer` global: `readOutline` (the in-memory outline with Chrome IDs, once queued work is done), `settle` (match the windows waiting to be re-linked now, then resolve once that's done), `outlineCommand` (what the view's runtime message does), `focusWindow` (Chrome's window focus event), `useTestSync` (point sync at a fake Drive with a fixed token), `syncNow` (push, then pull; the e2e build never pushes on its own), `syncState` (the picker state), `panelWindows` (windows whose docked panel is connected).
  - Live rows carry `data-window-id`, `data-group-id`, and `data-tab-id` (the Chrome ID) for locators.
  - Routes only apply once Playwright has attached to a tab, so background tabs the service worker opens must start on a placeholder and navigate after (`openBackgroundTabs` in `preview.spec.ts`), or they silently load Chrome's error page.
