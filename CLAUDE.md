# Tab Hammer — project instructions

Tab Hammer is a Manifest V3 Chrome extension (TypeScript + React + Vite) that shows every Chrome window, tab group, and tab as an outline in its own window, plus an MCP server that lets Claude Code read and rearrange tabs through the extension. It's an npm workspaces monorepo: `packages/extension` (the extension), `packages/mcp` (MCP server and native messaging host), `packages/protocol` (message types both compile against). Global CLAUDE.md owns workstyle, worktrees, and parallel-dev rules; this file adds Tab Hammer specifics.

## Launch Claude from the repo root

Always launch Claude in the repo root, not from a worktree directory — Claude Code resolves `.claude/` settings and skills from where it starts. Create and enter worktrees from there.

## Worktree setup

After `git worktree add`, run `npm install` at the worktree root. A fresh worktree has no `node_modules/`, and Node's resolver silently walks up to the main checkout's instead of failing.

## Completion gates

Pick the gate by change class. Report the gate name and result when declaring work complete.

| Gate            | Command        | When                                                                                                                      |
| --------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Docs-only diff  | (none)         | Every changed path is `.md`.                                                                                              |
| Any code change | `npm run gate` | typecheck + lint + format check + unit (Vitest) + `build:e2e` + e2e (Playwright, real Chromium with the built extension). |

Run it once on the final commit. The e2e suite launches its own throwaway Chromium profile; it never touches the user's Chrome.

The gate builds into `packages/extension/dist-e2e/` (`npm run build:e2e`), and the e2e fixture loads the extension from there. `~/.tab-hammer/dist` belongs to the user: every tree's `npm run dev` server writes it and their Chrome loads it, so never build into it from a gate or test run, and never run `npm run dev` yourself. `dist/` is only the `npm run build` output. To run e2e alone, `npm run build:e2e` first; pass Playwright arguments after `--` (`npm run test:e2e -- tests/e2e/bridge.spec.ts`).

Never run `npm run install-mcp` yourself: it writes into the user's Chrome profile folders and their Claude Code config. Tests deploy the native host into their own temp folder.

The e2e suite runs headless (new-headless Chromium). Headless Chromium ignores window focus changes, so window focus is asserted via recorded `chrome.windows.update` calls rather than by observing which window is focused. It must stay headless: the user works on this machine while gates run, and headed windows steal their workspace.

## Architecture in one breath

Extension paths below are relative to `packages/extension/`.

A service worker opens or focuses the Tab Hammer popup window, and screenshots each window's visible tab as the user browses (`src/background/previews.ts`) into an IndexedDB store keyed by page URL (`src/shared/previewStore.ts`), which the view reads for the tab preview panel. When the panel shows a window's visible tab with no preview, the view asks the service worker to capture it on demand, without the debugger. Background tabs are screenshotted through `chrome.debugger` and CDP `Page.captureScreenshot`, attached only for the shot (`src/background/debuggerCapture.ts`, one at a time through `captureQueue.ts`), and only from the explicit Refresh runs (`allowDebugger` on the capture request): the debugger's "started debugging this browser" infobar pushes the outline down under the pointer, so a hover must never attach it. It also records each window's and each on-demand tab's latest capture outcome (saved, or which rule skipped it, or the error) in `chrome.storage.session` (`src/shared/captureOutcomes.ts`); the preview panel shows it when a tab has no preview. Previews never go stale: one is how the page looked the last time the user had it on screen, kept until they look at it again or ask for Refresh all. The Capture missing (tabs with no preview) / Refresh all actions run those captures for every tab, one at a time, from the view (`src/view/refresh/`); they wake sleeping tabs (discarded, or not loaded since a restart) with a background reload first, and the panel's "Capture missing" hint follows the same rule (`backgroundTabNote`). Window captures share one scheduler (`captureScheduler.ts`) with a per-capture time limit, so one hung Chrome call can't stall the rest. Clearing Chrome's history deletes the matching previews (`history.onVisitRemoved` in `previews.ts`), and none of those pages gets a preview saved again until it's visited again (`historySuppression.ts`), so a capture already queued can't put one back. The service worker owns the outline (`src/background/outline/`): a record per window, group, and tab, keyed by Tab Hammer's own random IDs and kept in IndexedDB `tab-hammer-outline`; Chrome's IDs are attached only while a record is live. Chrome events are reconciled into it through a serial queue. A fresh browser launch is told apart from a worker restart by `browserSession` (the single instance in `src/background/session.ts`), and after a launch restored windows are re-linked to their saved records once their tabs stop changing (a quiet period), by the pure matcher in `src/model/outline/`. Closing a tab in Chrome removes its row, and closing a window by hand moves it to the trash. Hibernating a window or tab closes it in Chrome but keeps its rows, dimmed, to reopen on click; deleting moves a row to the trash; and the Recently closed section restores trashed rows for seven days. Windows Tab Hammer opens itself (including through the Claude bridge) are recorded as known, never re-linked, and windows and tabs it is closing are left out of reconciling until Chrome reports them gone. The view doesn't read Chrome for the tree: it subscribes to the outline over the `tabHammer.outline` port (`src/view/chrome/outlineClient.ts`) and sends commands (rename, hibernate, delete, restore) as runtime messages. `src/model/buildTree.ts` turns the outline into the window/group/tab view model, and `src/view/chrome/chromeSource.ts`, the only view module that touches `chrome.*`, keeps just the direct live actions (activate, focus, move, close). `src/model/selection.ts` is the pure multi-select reducer. Then it renders React components. The Claude bridge below stays live-only and never sees hibernated or trashed rows. The view has a fixed header above the outline and a fixed preview panel below it, and only the outline list scrolls between them: the search box, the Actions menu, live progress (with Stop), and banners go in that header (`src/view/header/AppHeader.tsx`), never in the scrolling list. Bulk actions (Close duplicates, Capture missing, Refresh all, Clear previews) live in `src/view/header/useHeaderActions.ts` and appear in both the header's Actions menu and a right-click on the outline's background; add new ones there, not as header buttons. The preview panel (`src/view/preview/PreviewPanel.tsx`) takes its own space in the window's column, so it never covers rows: it shows the tab last hovered (after a short rest) or moved to with the keyboard cursor, and keeps it when nothing is hovered (`usePreviewTarget.ts`); it collapses to a thin bar and resizes from its top edge, and both are remembered in `chrome.storage.local` (`src/view/chrome/panelSettings.ts`). There is no floating hover card. Window headers are sticky section bars in a colour picked from the window's Tab Hammer ID (`src/model/windowColor.ts`). In `npm run dev`, crxjs's service worker forwards every request to the extension's own origin to the Vite server; `build/faviconPassthrough.ts` exempts Chrome's `_favicon/` endpoint, and any other Chrome-served extension URL would need the same. crxjs also reloads the whole extension whenever a file the service worker imports changes; `build/holdBrokenReloads.ts` holds that reload while the service worker's files don't link (a half-finished edit), since a service worker that fails to start takes crxjs's reload client down with it and the extension stays dead until reloaded by hand. Chrome window and tab IDs are not stable across restarts, which is why the outline carries Tab Hammer's own IDs.

Sync (`src/background/sync/`, pure logic in `src/model/sync/`): each install writes one file, `outline-<installId>.json` (its exported outline, trash included), to Google Drive's hidden app-data folder, and only reads the others', so there's no merging. The sync engine (`syncEngine.ts`) pushes 10s after the outline last changed (a dirty flag in `chrome.storage.local` survives a worker restart), pulls every 5 minutes (`chrome.alarms`) and when the picker opens, downloading only files whose Drive modified time changed into a local cache (IndexedDB `tab-hammer-sync`), and validates every file against the schema both ways (`src/model/sync/schema.ts`). Nothing remote changes this computer's outline except Restore all, or the self-restore of an install whose outline database started empty (no push happens until that check is done); self-restore brings the file's live windows in as re-link candidates and runs the restart matcher over the open windows, so they don't show twice. Checkpoints are dated snapshots of this computer's outline, local and in Drive, one a day plus one before anything drastic, pruned to 14 daily then 8 weekly. Drive sits behind `SyncBackend` (`driveBackend.ts`: REST with `fetch`, `chrome.identity.getAuthToken`, a 401 drops the cached token and retries once). Drive sync is off until `GOOGLE_OAUTH_CLIENT_ID` in `src/shared/syncConfig.ts` is set; the manifest's `oauth2` block exists only then, and never in the e2e build. Chrome Sync devices (phones included) come from `chrome.sessions` (`devices.ts`), no Drive needed. The Actions menu's "Other devices…" opens a devices panel in the header's banner area (`src/view/sync/`) that shows any of them, or a checkpoint, read-only in place of the outline (its banner also in the header), with Open here (a copy with new IDs), Restore all (missing windows come in hibernated), and Forget; it talks to the worker over the `tabHammer.sync` port and sync command messages.

Claude bridge: Claude Code starts the MCP server (`packages/mcp/src/main.ts`, stdio). Chrome starts the native messaging host (`packages/mcp/src/host.ts`) when the service worker connects (`src/background/bridge.ts`, at startup and on toolbar click; it retries with backoff if the host exits, and stops if the host isn't installed). The two meet on a Unix socket (`~/.tab-hammer/bridge.sock`; `TAB_HAMMER_SOCKET` overrides it). The host only relays, rewriting request IDs so several Claude sessions can share one Chrome connection; the service worker runs each command (`src/background/tabCommands.ts`). Chrome runs a deployed copy of the host from `~/.tab-hammer/native-host` (`packages/mcp/src/deploy.ts`), never the repo: macOS blocks Chrome-launched programs from reading `~/Documents` until the user approves a prompt, so a host run from the repo hangs silently. Keep `host.ts` and what it imports free of npm packages, and list every file it needs in `deploy.ts`. `packages/mcp` runs as TypeScript directly on Node 22.18+ (type stripping): erasable syntax only, `.ts` import extensions.

## Tests

- Unit: `packages/*/src/**/__tests__/` (and `packages/extension/build/__tests__/` for the Vite plugin, run against the installed crxjs). Extension: model, outline model (`src/model/outline/`: lifecycle, matching, reconcile, match application, open/place), outline store (against `fake-indexeddb`) and settle tracker (`src/background/outline/`), browser-session renewal, capture scheduling, per-window and on-demand debugger capture with an injected `chrome`, the capture queue, preview policy, sync (`src/model/sync/`: schema validation, Restore all, Open-here copy, checkpoint retention, device list; `src/background/sync/`: the engine against an in-memory backend with a fake clock, the Drive backend against `tests/fakeDrive.ts`, the sync store, `chrome.sessions` with a stubbed `chrome`)), pure logic only. MCP: native messaging framing, plus a functional test running the real MCP server process against the real relay with a stand-in extension.
- E2E: `packages/extension/tests/e2e/`. `bridge.spec.ts` covers the whole Claude → Chrome path: it deploys the native host into a temp Chromium profile's `NativeMessagingHosts` folder, lets Chromium launch it, and drives tab commands through the real MCP server. The fixture opens the view through the service worker's `tabHammer.openOrFocus` test hook, the same code path as the toolbar click. Chrome refuses to screenshot `data:` pages, so preview tests serve http pages through Playwright's `context.route`. `outline.spec.ts` covers the outline's lifecycle in the live view (hibernate, delete, Recently closed), and `restart.spec.ts` is a real restart: it closes Chromium and relaunches it on the same profile with `--restore-last-session`, then checks restored windows re-link to their rows (served by a local page server, since restored tabs load before Playwright can route them). `sync.spec.ts` runs two installs (two temp profiles) against one fake Drive (`tests/fakeDrive.ts`, served over HTTP by the test): the devices panel, Open here, Restore all, checkpoints, and a wiped profile's self-restore re-linking its open windows. Tests never reach Google. Test hooks on the service worker's `tabHammer` global: `readOutline` (the in-memory outline with Chrome IDs, once queued work is done), `outlineCommand` (what the view's runtime message does), `useTestSync` (point sync at a fake Drive with a fixed token), `syncNow` (push without the 10s wait, then pull), `syncState` (the picker state). Live rows carry `data-window-id`, `data-group-id`, and `data-tab-id` (the Chrome ID) for locators. Routes only apply once Playwright has attached to a tab, so background tabs the service worker opens must start on a placeholder and navigate after (`openBackgroundTabs` in `preview.spec.ts`), or they silently load Chrome's error page.
